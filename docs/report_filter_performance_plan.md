# Report Filter Performance Plan

## Purpose

This plan addresses report-performance issues caused by expensive report-time filters, especially text-search filters over property/address fields and repeated filter-table logic generated by Power BI visuals.

The target fix is to move stable filtering and classification logic into the Fabric data layer, then keep Power BI filters as simple boolean or low-cardinality column filters.

## Current Repo Check

The repo does not contain a Power BI report definition file such as `.pbix`, `.pbip`, `.Report`, or extracted visual JSON. Because of that, the actual visual query DAX generated by Power BI cannot be inspected here.

`docs/semantic_model.md` is the documented DAX source of truth for this repo.

Search results in the repo and documented DAX:

- No stored `SEARCH`, `FIND`, `CONTAINSSTRING`, `SUMMARIZECOLUMNS`, or `__DS0FilterTable` report-query logic was found.
- The documented semantic-model measures do not currently use text-search DAX.
- The documented benchmark measures use repeated `SUMX ( VALUES ( fact_vacancy_interval_vic[vacancy_id] ), ... )` iterators.
- The documented row-visibility filters use dynamic overlap measures:
  - `Vacancy Overlaps Selected Period`
  - `Property Overlaps Selected Period`
- The documented report model uses `dim_property_vic[property_short_address]` as a displayed field.
- The repo now defines `dim_property_vic[is_standard_address]` as the first data-layer flag for replacing report-time address text searches.
- Date-sliced day measures correctly come from `fact_vacancy_day_vic`.

This means the text-search issue is likely in the live Power BI report visual filters or generated visual queries, not in the documented semantic-model measures. The documented DAX still has optimization candidates around repeated iterators and visual-level overlap filters.

## Issue 1: Address/Text Search At Report Runtime

### Problem

If the report filters out bracketed or non-standard address/property values using DAX text functions, Power BI has to scan text values during query execution.

Problem patterns include:

```DAX
SEARCH(...)
FIND(...)
CONTAINSSTRING(...)
FILTER ( dim_property_vic, ... text condition ... )
```

This is expensive compared with filtering a boolean column.

### Data-Layer Fix

Add a boolean column to `dim_property_vic` in `vacancy_reporting_vic_notebook.py`:

```text
is_standard_address
```

Implemented initial rule:

```text
TRUE  = property_short_address does not contain bracket markers: < > [ ] ( )
FALSE = property_short_address is blank or contains one of those bracket markers
```

The exact source field used by the live report filter still needs confirmation. Candidate fields:

- `property_short_address`
- `ownership`
- `property_program`
- `property_source`

The example report output shows bracketed values such as `<BlueCHP>` under `Ownership`, not `Property Address`. If the live report is filtering ownership rather than address, add a separate flag with a clearer name instead of overloading `is_standard_address`.

### Report Fix

Replace text-search filter logic with one of these:

Preferred visual/page/report filter:

```text
dim_property_vic[is_standard_address] = TRUE
```

If it must remain inside a measure:

```DAX
KEEPFILTERS (
    TREATAS ( { TRUE }, dim_property_vic[is_standard_address] )
)
```

## Issue 2: Repeated Filter Tables In Visual Queries

### Problem

Power BI visuals commonly generate separate filter-table variables such as:

```DAX
VAR __DS0FilterTable = ...
VAR __DS0FilterTable2 = ...
VAR __DS0FilterTable3 = ...
VAR __DS0FilterTable4 = ...
```

When several filters are combined inside `SUMMARIZECOLUMNS`, the engine can spend time building and applying large filter combinations before evaluating the measure.

Not all generated filter tables are avoidable, especially for slicers. The target is to remove expensive or repeated calculated filters, not normal slicer filters.

### Data-Layer Fix

Create simple reusable flags in `dim_property_vic`, for example:

```text
is_standard_address
is_reportable_property
is_vic_property
```

Use `is_reportable_property` for stable business-scope filtering if several conditions are always applied together.

Example concept:

```text
is_reportable_property =
    state = "VIC"
    and is_standard_address = TRUE
    and property_id is not null
```

Only add each flag after confirming the business meaning. Do not hide unconfirmed rules inside the model.

## Issue 3: Repeated Benchmark Iterators

### Current Documented DAX

`docs/semantic_model.md` currently defines four benchmark measures in this pattern:

```DAX
Vacancies LE 21 Days =
SUMX (
    VALUES ( fact_vacancy_interval_vic[vacancy_id] ),
    IF ( CALCULATE ( [Vacancy Days] ) <= 21, 1, 0 )
)
```

The same iterator pattern is repeated for:

- `Vacancies LE 21 Days`
- `Vacancies GT 21 Days`
- `Vacancies LE 48 Days`
- `Vacancies GT 48 Days`

### Risk

Each measure iterates vacancy IDs and recalculates `[Vacancy Days]` per vacancy. On visuals that show several benchmark measures together, Power BI can repeat similar work multiple times.

This is not the same issue as text-search filtering, but it can contribute to slow visuals.

### Fix Options

Keep these measures for correctness until performance data proves they are a bottleneck. They are selected-period measures and should still respect the date slicer.

If Performance Analyzer shows benchmark measures are slow, test optimized alternatives:

```DAX
Vacancies LE 21 Days =
COUNTROWS (
    FILTER (
        VALUES ( fact_vacancy_interval_vic[vacancy_id] ),
        [Vacancy Days] <= 21
    )
)
```

This may read more clearly but may not materially change the storage-engine plan. Validate with Performance Analyzer before replacing all benchmark measures.

Do not replace selected-period benchmark measures with static interval flags such as `meets_21_day_benchmark` unless the business wants lifetime vacancy benchmark classification instead of selected-period classification.

## Issue 4: Dynamic Overlap Visual Filters

### Current Documented DAX

The report docs recommend using:

```DAX
Vacancy Overlaps Selected Period
Property Overlaps Selected Period
```

as visual-level row filters.

### Risk

These measures are dynamic and use selected dates plus interval start/end fields. If applied to large detail visuals, they can add report-time work.

`Vacancy Overlaps Selected Period` may be redundant on visuals where the `dim_date` slicer already filters `fact_vacancy_day_vic`, and the bidirectional `vacancy_id` relationship filters `fact_vacancy_interval_vic`.

### Fix Options

Validate page by page:

- Keep `Vacancy Overlaps Selected Period = 1` only where the visual would otherwise show non-overlapping rows.
- Remove it from visuals where the day fact relationship already filters intervals correctly.
- Use `Property Overlaps Selected Period` only where the business explicitly wants property-lifecycle filtering.

Do not precompute overlap flags in the lakehouse for arbitrary `From Date` / `To Date` selections. The selected reporting window is dynamic, so this logic either belongs to the date relationship path or remains a measure.

## Issue 5: Date-Sliced Measures Must Stay Day-Fact Based

### Current Status

The model docs correctly define these measures from `fact_vacancy_day_vic`:

```DAX
Vacancy Days =
SUM ( fact_vacancy_day_vic[vacancy_day_count] )

Tenantable Days =
SUM ( fact_vacancy_day_vic[tenantable_day_count] )

Untenantable Days =
SUM ( fact_vacancy_day_vic[untenantable_day_count] )

Other Days =
SUM ( fact_vacancy_day_vic[other_day_count] )
```

Do not replace these with interval-level columns for report-window calculations.

### Risk To Watch

If a visual uses interval-level lifetime columns such as `full_vacancy_days`, `full_tenantable_days`, `full_untenantable_days`, or `full_other_days`, it will not respect the selected `From Date` / `To Date` window.

The report detail table should use measures for day counts.

## Implementation Steps

### Step 1: Confirm Live Report Filters And Visual Query DAX

In Power BI Performance Analyzer, copy the DAX query from the slow visual and identify:

- which field is being text-searched,
- whether the condition is filtering address, ownership, property source, or another property field,
- whether the filter is visual-level, page-level, report-level, or embedded in a measure.
- whether benchmark measures or overlap filters dominate query time.

Save the copied DAX query outside the report or into a future troubleshooting note if needed.

### Step 2: Add Data-Layer Flags

Update `vacancy_reporting_vic_notebook.py`:

- add `is_standard_address` to `dim_property_vic`, completed in the repo,
- optionally add `is_reportable_property` if the same scope is reused across pages,
- preserve the original source fields for auditability.

Implemented conservative first implementation:

```text
is_standard_address =
    property_short_address is populated
    and no bracket marker appears in property_short_address
```

Do not remove rows from `dim_property_vic`; publish the flag and let the report filter it.

### Step 3: Update Documentation

Update:

- `docs/project_overview.md`
- `docs/fabric_implementation.md`
- `docs/semantic_model.md`
- `docs/report_pages.md`

Document:

- flag definition,
- source field used,
- whether the flag is applied globally or only on selected pages,
- that this is a data-layer classification used to avoid report-time text scanning.

### Step 4: Refresh Fabric And Semantic Model

Run:

1. `vacancy_reporting_vic_notebook.py`
2. semantic model refresh
3. report refresh

Confirm `dim_property_vic[is_standard_address]` appears in Power BI.

### Step 5: Replace Report Filters

For affected pages/visuals:

- remove DAX/text-search filters,
- add `dim_property_vic[is_standard_address] = TRUE`,
- use `dim_property_vic[is_reportable_property] = TRUE` if a combined flag is added.

Keep the existing date slicer on `dim_date[date]`.

### Step 6: Review Documented Measures

Review `docs/semantic_model.md` and the live model:

- confirm `Vacancy Days`, `Tenantable Days`, `Untenantable Days`, and `Other Days` use `fact_vacancy_day_vic`,
- test benchmark measures with Performance Analyzer,
- keep selected-period benchmark measures unless lifetime benchmark classification is explicitly requested,
- remove overlap visual filters only where relationship filtering gives the same row set.

### Step 7: Validate Results

For each affected page:

- row counts match the previous intended exclusion behavior,
- expected properties with bracketed markers are excluded or included according to the confirmed rule,
- `Vacancy Days = Tenantable Days + Untenantable Days + Other Days`,
- selected-period counts still change correctly with `From Date` and `To Date`.

### Step 8: Validate Performance

Use Power BI Performance Analyzer before and after:

- record visual query duration,
- confirm text-search DAX no longer appears in copied visual queries,
- confirm filters use boolean columns or simple `TREATAS({TRUE}, ...)` instead.

## Proposed Acceptance Criteria

- No production visual uses `SEARCH`, `FIND`, or `CONTAINSSTRING` for stable property/address exclusions.
- `dim_property_vic` contains `is_standard_address`.
- Any repeated stable business-scope filtering is represented by a simple data-layer flag.
- Report day-count measures remain based on `fact_vacancy_day_vic`.
- Dynamic overlap filters are used only where they are needed.
- Benchmark measures are verified against Performance Analyzer before and after any DAX rewrite.
- Slow visuals show measurable improvement in Performance Analyzer.
